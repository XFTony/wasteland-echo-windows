## 有价值，但应先测量或收窄

| 建议 | 核验及修订 |
|---|---|
| 拆 GameModel、抽 MetaFacade/RunSession | 现已抽出 CombatSim、SpawnSystem、BossSystem、MenuSession；仍有单局和 Meta 耦合。按真实变更痛点渐进拆，少于 400 行不是验收目标。 |
| 构造时不写盘 | GameModel 构造末尾确实 persist；SaveManager 现在会先保留损坏原文。要先定义迁移提交边界，不能只删除写入。 |
| 统一 SaveScheduler 400ms 防抖 | 直接写入点确有多处，但购买、奖励、局末低频且关乎进度。先量写入频率；连续设置可合并，关键交易立即写。beforeunload 不能作为唯一保障。 |
| fireWeapon 的 enemies.find 改 Map | 代码确实每次开火查目标，但敌人数有硬上限。Map 需同步对象池生命周期；先做热点采样再决定。 |
| checkJs、lint、CI、E2E | 195 项 Node 测试和点状浏览器 QA 已有；可先固化少量黄金路径，再渐进引入静态检查，避免历史噪声。 |
| 600 秒 RSS 警戒线 | Node 压力局使用极高生命值；峰值约 100–130 MiB 不能单独证明泄漏。需多轮趋势、堆快照与 WebView2 长局。 |
| config 与菜单分文件 | ContentRegistry 已校验内容引用，渲染原语已拆分；以新内容或 UI 改动的真实耦合为依据。 |
| hit-stop 和音频总线 | 可试验，但会改变战斗时序和无障碍体验；先测受击辨识度与声音并发。 |

## 建议执行顺序

1. Git 基线已完成；下一步取得七局真人记录，并做便携版重启、安装卸载、存档保留及 WebView2 长局验证。
2. 根据真人记录处理背包/商店/结算、敌弹和 Boss 信息，以及撤离信标目标语言；再扩展多 seed 平衡矩阵。
3. 数据可靠性优先做可导出、可恢复、状态可见。是否防抖及如何拆会话，取决于实际写入频率和耦合。
4. 新机制与内容逐项原型化，每项保留独立提交和可回退验收。
