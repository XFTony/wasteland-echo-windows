# 《荒原回响》游戏引擎选型与迁移评估

日期：2026-10-29。性质：基于当前源码的选型研究与建议，不代表已批准或完成引擎迁移。

后续已使用本机Godot 4.7.2完成隔离技术验证，见[本机工具与迁移报告](godot-local-feasibility-2026-10-29.md)。本文件保留初次选型时的观察，武器扩展现已收尾；当前迁移范围以新报告为准。

## 1. 结论与适用前提

**Godot 适合本项目的长期方向；当前适合做有明确边界的试迁移，不适合立即替换整个项目。**

如果从零开始，为 Windows 桌面的紧凑像素、俯视角、自动攻击、走位生存游戏选择工具，我会优先选择 Godot。现在已有相当数量的玩法、存档、碰撞、输入与测试，因此决定应依据“未来制作效率能否覆盖迁移成本”，而不是仅看引擎是否能运行同类游戏。

推荐顺序：先完成当前武器扩展的必要验收并保存可回退基线；再做一个使用现有素材的 Godot 对照样板；通过制作效率、操作一致性与实际设备性能比较后，选择一个主开发环境。若不迁移，优先补地图与武器编辑工具，而不是不断扩充自制通用引擎。

本次只新增本评估文档，没有安装引擎、修改运行代码、改动存档、发布版本或宣称新引擎已通过性能验收。

## 2. 本次核实的项目状态

| 项目 | 当前核实结果 | 对选型的影响 |
|---|---|---|
| 类型与平台 | Windows 10/11 优先的俯视角废土生存射击；浏览器用于开发；Tauri 2 + WebView2 提供桌面窗口 | 文件夹仍叫 Wechat games，但不能因此把微信小游戏当作现行发布目标 |
| 主体验 | 自动瞄准与射击，玩家走位、拾取、升级，返回地图交易站购物，连续生存，时间增强敌群 | 原生 2D 引擎适用；不需要因更换引擎改成波间购物 |
| 基础框架 | JavaScript/CommonJS、Canvas 2D；运行时零 npm 依赖；固定 60 Hz，最多追赶 4 步 | 已有自制的专用游戏框架，迁移不是给现有项目安装一个插件 |
| 系统边界 | core、content、world、render、input、platform、runtime 分层 | 游戏规则可作为迁移规格；若改用 JavaScript 框架，部分规则代码可以直接复用 |
| 战斗与资源保护 | 对象池、空间网格、三档导航、实体硬上限；默认上限为 128 敌人、180 友弹、120 敌弹、140 拾取物 | 不能因引擎自带物理或导航就删掉现有优化策略 |
| 内容 | 三张地图；新像素巡线者、八类像素敌人；原七枪；工作区另有三件远程及两件近战扩展 | 已认可图像可保留；新武器仍需收尾验收，不应以未验收状态作为迁移性能基线 |
| 人物结构 | 身体、武器、手套、袖口独立，有连续瞄准与动作表现 | 可以映射为 Godot 分层节点；不需要重画或恢复 Blender 人物 |
| 存档 | `src/core/save.js` 当前 schemaVersion 为 10，以浏览器存储接口保存 | Godot 桌面版需显式导入旧档，不能默认读取 WebView2 的存储 |
| 验证资产 | 当前武器扩展的已有测试日志记载 326 项通过；本次没有重新运行该套测试 | 测试可作为规则依据；JavaScript 测试不会自动成为 Godot 测试 |
| 性能证据 | 现有 Edge 无界面报告覆盖 720p/80 敌、1080p/120 敌、720p/104 敌与四塔 | 只能说明本机既有场景结果，不能证明新武器负载、真实窗口或最低配置表现 |
| 尚缺 | 明确的最低目标电脑、可投入时间与预算、本人愿意学习编辑器的程度 | 迁移工期与最低硬件结论只能给条件判断 |

## 3. Godot 能解决什么

Godot 官方展示页收录《土豆兄弟》。这证明技术路线适用于同类产品；它不证明本项目直接照搬某种节点结构就能取得相同性能，也不等于能取得《土豆兄弟》的源代码或素材。[官方案例](https://godotengine.org/showcase/brotato/)

| 当前制作任务 | 可采用的 Godot 方法 | 预期收益 | 仍需自己完成 |
|---|---|---|---|
| 摆放建筑、交易站、掩体和出生点 | 场景编辑器、TileMapLayer、对象场景、碰撞形状编辑 | 可以直接查看摆放与碰撞关系，减少手工改坐标后的反复截图 | 地图空间节奏、通路宽度、卡怪排查、遮挡规则 |
| 主角持枪、跑步、近战 | Sprite2D/AnimatedSprite2D 分层，AnimationPlayer 预览与属性轨道 | 在编辑器查看枪、手、身体、前后遮挡与动作时间 | 素材质量、脚步接地、手与握点匹配、攻击范围与有效时机 |
| 抛壳、枪焰、激光、砸地 | 可复用效果场景、Line2D、精灵序列、受控粒子 | 调颜色、寿命、偏移和曲线时可即时观察 | 武器辨识、危险可读性、效果数量限制和低闪光方案 |
| 背包、商店、升级卡 | Control、Container、Theme、焦点与动画 | 多分辨率布局、复用样式、可视化调整较方便 | 信息层级、中文排版、键鼠和手柄全流程检验 |
| 新增武器、敌人与道具 | 自定义 Resource、复用场景、Inspector 导出属性 | 数值和资源引用可在编辑器中调整，减少散落的专用分支 | 稳定 ID、引用校验、技能规则、平衡与来源记录 |
| 声音与混音 | AudioStreamPlayer、总线、限声道管理 | 逐枪试听与音乐/音效分组更直观 | 好的录音、包络、混音、循环点与真实听审 |
| 桌面运行 | Godot 原生 Windows 导出 | 可替代 Tauri/WebView2 运行结构，统一游戏内调试工具 | 包体、启动、驱动兼容、存档迁移与安装分发实测 |

官方依据：[2D 工具概览](https://docs.godotengine.org/en/stable/tutorials/2d/introduction_to_2d.html)、[TileSet 碰撞与自定义数据](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html)、[AnimationPlayer](https://docs.godotengine.org/en/stable/classes/class_animationplayer.html)。

编辑器最有价值的地方是缩短“修改—预览—纠正”的距离，不是自动把画面变精美。换到 Godot 后，一张人物图片仍是一张图片；想得到新的跑步姿态，仍需制作动作素材，或设计合适的分层动画。

## 4. 必须认识的迁移成本

### 4.1 不能直接运行现有 CommonJS 游戏

Godot 官方支持 GDScript、C#，以及经 GDExtension 接入的 C/C++。现有 JavaScript 不是它的官方内置游戏脚本语言。[官方脚本说明](https://docs.godotengine.org/en/stable/getting_started/step_by_step/scripting_languages.html)

可以找到社区 JavaScript 绑定，但不能据此承诺原项目无成本搬入。为了继续保留 JavaScript 而引入额外脚本运行层，会增加导出、调试和维护变量；本项目没有证据表明值得走这条路线。把现有游戏放进一个网页窗口，也不能获得 Godot 原生编辑和渲染的主要收益。

建议正式试迁移采用带类型标注的 GDScript；先不引入 C#、C++ 或额外脚本绑定。只有性能分析确认瓶颈后，再考虑局部低层实现。

### 4.2 哪些能保留，哪些要改

| 内容 | 复用方式 | 成本判断 |
|---|---|---|
| 人物、敌人、武器图、音效、音乐、字体 | 使用原运行素材重新导入，检查纹理过滤、透明边缘、压缩与循环 | 复用程度高，但不是零检查 |
| 原生矩形描述的新武器 | 在构建工具中导出透明 PNG，保留描述文件作为源文件 | 不需要重新设计武器形象；需适配导出 |
| 内容 ID、数值、价格、掉落定义 | 从旧内容注册表导出结构化数据，再转为 Godot Resource/数据文件 | 规则复用高；旧 JS 定义不直接等于 Godot 资源 |
| 地图几何与交易点 | 导出 world 数据，转换为场景或编辑器可用数据 | 应先保持原几何与碰撞，避免迁移时同时重画三图 |
| 手、袖口与枪的握点 | 转成分层节点、锚点与朝向规则 | 可保留设计成果；旧 Canvas 合成器要替换 |
| 自动锁定、弹道、近战、敌人、塔台、成长、交易 | 依据原规则移植，并用样例验证 | 改造量大；细节最容易在重写中回退 |
| Canvas 界面与点击区域 | 用 Godot UI 重建 | 需重做，图片和布局意图可保留 |
| 存档 | 旧程序导出 JSON，新程序验证并导入到 `user://` | 必须保护所有权、货币、设置、稳定 ID、版本和备份 |
| 测试 | 复用输入、场景、期望行为和跨语言数据夹具 | 数值比较可设容差；不能假设不同随机数与浮点实现逐帧相同 |
| Tauri、WebView2、浏览器平台层 | Godot 原生发布时由引擎对应能力替代 | 需要重新建立构建、保存目录、窗口与发布检查 |

不要同时用 Godot 自动物理碰撞和移植的自制判定对同一攻击结算两遍伤害。近战与高速弹继续显式检查连续扫掠；动画轨道负责表现，实际伤害仍由固定逻辑时序决定。

## 5. 其他方案的适配比较

| 方案 | 最有价值的地方 | 对当前项目的代价 | 判断 |
|---|---|---|---|
| Godot | 完整可视化 2D 制作、场景、动作、UI、音频、原生桌面导出 | 玩法代码移植，Canvas 表现与 UI 重建，学习编辑器 | 长期首选候选；先做对照样板 |
| Phaser | JavaScript/TypeScript，与现有逻辑语言一致，提供场景、资源、动画和渲染体系 | 渲染、输入与生命周期仍需改造，已有基础设施会部分重叠 | 适合明确坚持 JavaScript 的方向；代码复用更好，但未必最能减少本人美术编辑负担 |
| GDevelop | 可视化事件与行为，降低本人编写一般交互的门槛 | 本项目已有复杂定制规则，重建事件与代码边界仍有成本 | 若长期目标是本人尽量少写代码，可另作选择；当前没有充分收益支持优先迁移 |
| 保留现有框架，接入 Tiled | 地图对象、碰撞与交互点可视化；运行时继续使用已有 world 数据 | 需要一次性导入/导出适配 | 短期成本最低，特别适合地图成为主要瓶颈的情况 |
| 只替换为 PixiJS 类渲染库 | 可能改善批量精灵渲染与图形效果 | 仍需自己维护规则、UI、输入、关卡与制作工具 | 不等于完整引擎迁移；只有实际渲染瓶颈成立才值得选 |

Godot、Phaser、GDevelop 的所查核心仓库采用 MIT 许可。引擎许可不自动涵盖第三方插件和素材。使用 Godot 一般下载安装官方编辑器和导出模板即可，无须克隆并编译整个引擎源码。

来源：[Godot 仓库](https://github.com/godotengine/godot)、[Phaser 仓库](https://github.com/phaserjs/phaser)、[GDevelop 仓库](https://github.com/4ian/GDevelop)。Phaser 的网页与桌面发布结构不同于 Godot 原生导出，不能把“同为 2D 引擎”理解成同一种运行方式。

Tiled 支持对象层、自定义属性和 JSON。适配本项目时，可把建筑图像、矩形碰撞、交易站交互区、出生区分层编辑，再在构建时转换成 WorldRegistry 所需数据；仅让构建工具依赖编辑器格式，不给游戏添加额外运行负担。编辑器文件应成为该地图的唯一可编辑来源，生成文件不再手工修改。[Tiled JSON 官方格式](https://doc.mapeditor.org/en/stable/reference/json-map-format/)

LDtk 也可作为地图工具候选，具有 JSON 数据格式；考虑本项目现有自由摆放的建筑与矩形对象，建议先用 Tiled 试验，而不同时维护两个地图导入器。[LDtk 官方格式](https://ldtk.io/docs/game-dev/json-overview/)

## 6. 性能、启动与低配判断

1. **不能承诺换引擎自动更快、更省内存或包体更小。** 原生导出减少了 WebView2 依赖，但有自己的引擎、纹理、音频和场景开销；最终看同内容实测。
2. Godot 试验优先使用 Compatibility 渲染方式。官方把它列为老旧/低端设备及一般 2D 游戏的适用选择。不要为了枪焰和纸卡动画默认启用重型光照、后处理或 Forward+。[官方渲染器选择](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)
3. 先验证目标机器的显卡与驱动；“最低配置越低越好”仍需落到一台具体低配电脑。官方编辑器配置、简单导出项目配置、本游戏最终配置必须分开理解。[官方系统要求](https://docs.godotengine.org/en/stable/about/system_requirements.html)
4. 延续对象池、敌群实体上限、有限效果池、可见区域裁剪、共享导航思想。高数量敌人不先套用最重的节点/寻路/碰撞组合；按测量结果选择集中式管理或更细的节点组织。
5. 比较时使用同一台机器、相同窗口分辨率、相同素材和相同负载；对比现有 Windows 包与 Godot 原生导出包，不用 Godot 编辑器运行去对比无界面 Edge。
6. 测量至少包括：冷启动到可操作时间、进入地图时的卡顿、完整进程树内存、工作集趋势、帧时间 p95/p99、射击与拾取峰值、30 分钟长局。JS heap 不能当作 WebView2 游戏总内存。
7. 粒子和激光不能遮住敌弹，降低闪光/抖动后仍需表达攻击范围。视觉变丰富不能成为改变伤害判定的理由。

目前没有本项目 Godot 样板的运行结果；任何性能优势都仍是待验证假设。

## 7. 推荐执行路线与工作量

以下是规划估算，按一名熟悉对应技术的开发者的有效人日计算，不是工期承诺；不包含重新制作美术、等待设备、商店上架和学习成本。个人边学边做通常会更久，样板完成后应重新估计。

| 顺序 | 阶段 | 具体方法与交付 | 建议工作量 | 通过条件 |
|---|---|---|---|---|
| 0 | 固定当前基线 | 收尾新武器方向板与小窗口截图、交互/性能回归、素材来源、可试玩 Windows 包；按既定 Git 规则保存 | 属于已有武器任务，另按未完成项估计 | 能回退，已知问题清楚，不把旧 exe 当成新代码效果 |
| 1 | 迁移清单和数据样本 | 固定内容 ID；导出一张图、三件武器、两类敌人、存档样本和素材对应关系 | 1～2 人日 | 样板不重画素材、不另调战斗数值；数据来源明确 |
| 2 | Godot 可玩对照样板 | 一张图的代表区域，默认巡线者，手枪、激光、锤，两类敌人；走位/自动攻击/碰撞/拾取/一次升级/交易/死亡重开 | 4～8 人日 | 操作和规则可与现版逐项比较；不能只看人物站立截图 |
| 3 | 测量和本人编辑试验 | 相同战斗压力；导出 exe；实测启动、帧时间、内存；本人修改枪口位置、摆一个掩体、调一次攻击效果 | 2～4 人日 | 本人能理解操作，制作过程明显缩短，性能不出现不可接受回退 |
| 4 | 是否全面迁移的决策 | 写出收益、代价与未解决问题；只保留一个主开发环境 | 不单独承诺天数 | 样板不通过则保留现有技术路线；不长期维护两套完整游戏 |
| 5 | 全内容与外围系统 | 其余武器/敌人/三图、塔台、成长、装备、全套 UI、音频、设置、键鼠/手柄、旧档导入、发布脚本 | 12～25 人日，需样板后重估 | 稳定 ID 与核心体验保留；全内容可用，存档导入可追溯 |
| 6 | 完整回归与发布准备 | 自动规则检查、真实设备长局、低配、分辨率/缩放、实体手柄、安装与保存路径 | 5～10 人日，依设备与缺陷数量变化 | 达到既定发布清单后再对外；不提前打版本标签 |

只把第 1～3 阶段作为首次可决策投入：约 7～14 个有效人日的粗估，范围仍有不确定性。后续阶段不是已排定的承诺；不能把试迁移样板成本当作整个游戏搬迁成本。

### 样板的六项验收

- 风格：使用当前认可的人物和敌人，保留手/袖口/枪独立；像素过滤、前后层次、八方向持握无明显回退。
- 规则：激光碰墙停止；近战有前摇、有效段和结束；敌人不能穿建筑；购物暂停不消耗生存时间；新武器不能重复命中结算。
- 操作：自动锁定稳定；移动、暂停、失焦、切枪、重开与基本手柄动作可用。
- 制作：新增一件数据同类武器不改公共战斗循环；移动地图掩体后碰撞与视觉一起更新；音画接点可在编辑器检查。
- 性能：达到现行 60 Hz 目标；复用 80 敌、120 敌等负载，并补激光、爆炸、近战消弹和四塔场景；真实长局内存趋势稳定。目标电脑仍待指定。
- 可维护性：源数据和生成资源只有一个权威来源；有导出命令、运行说明、内容校验、素材来源和回退方法。

玩家场景继续分 Body、WeaponPivot、独立手与袖口、枪口和抛壳锚点；朝向改变时显式调整前后绘制层级。不要把手永久焊在枪图上。动画只驱动姿态与视觉，规则系统保持伤害时机的单一来源。

## 9. 决策建议

- 如果希望未来经常亲自调地图、动作、界面和特效，愿意学习节点、场景和资源：优先试 Godot，它更可能降低长期对专用代码修改的依赖。
- 如果目标是尽快完成当前游戏的可玩验证，主要仍由代码方式制作，近期不愿承担规则移植：先保留现有框架，补 Tiled 导入与有限的武器预览工具。
- 如果明确需要保留 JavaScript 并采用成熟游戏框架：再比较 Phaser；同语言迁移有优势，但不是把原 CanvasRenderer 原封不动套进框架。
- 当前没有理由因更换引擎而重做人物风格、改波次规则、推翻连续交易站或重新制作全部美术。玩法、美术和引擎应分开决策。

**最终建议：Godot 是值得认真试验的长期首选；先保住当前武器版本，再用一个可玩的对照样板决定是否全面迁移。**
